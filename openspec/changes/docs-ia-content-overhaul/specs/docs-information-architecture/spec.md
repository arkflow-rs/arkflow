## ADDED Requirements

### Requirement: Docs site exposes the canonical top-level sections
The current (next) documentation content root (`docs/docs/`) SHALL contain
exactly these top-level sections, each as its own directory with a
`_category_.json`: Introduction, Getting Started, Concepts, Configuration,
Components, SQL Reference, Processing Guides, Cookbook, Observability,
Operations, Troubleshooting, and Migration. No other top-level section SHALL
exist in the current content root.

#### Scenario: All twelve sections present
- **WHEN** the top-level directories of `docs/docs/` are listed alongside
  their `_category_.json` `label` fields
- **THEN** the set of labels equals {Introduction, Getting Started, Concepts,
  Configuration, Components, SQL Reference, Processing Guides, Cookbook,
  Observability, Operations, Troubleshooting, Migration}

#### Scenario: No extraneous top-level section
- **WHEN** a new directory is created directly under `docs/docs/`
- **THEN** it is rejected at review unless its `_category_.json` label is one
  of the twelve canonical sections

### Requirement: Top-level sections render in canonical order
Each canonical section's `_category_.json` SHALL set a numeric `position`
that orders the sections: Introduction=1, Getting Started=2, Concepts=3,
Configuration=4, Components=5, SQL Reference=6, Processing Guides=7,
Cookbook=8, Observability=9, Operations=10, Troubleshooting=11, Migration=12.
The sidebar SHALL be produced by Docusaurus `autogenerated` mode consuming
these positions.

#### Scenario: Sidebar reflects canonical order
- **WHEN** `cd docs && pnpm build` renders the sidebar
- **THEN** the section labels appear top-to-bottom in the order Introduction,
  Getting Started, Concepts, Configuration, Components, SQL Reference,
  Processing Guides, Cookbook, Observability, Operations, Troubleshooting,
  Migration

### Requirement: Every documentation page is reachable from the sidebar
Every Markdown file under the current content root (`docs/docs/**`) SHALL be
reachable from the autogenerated sidebar. No Markdown file SHALL be orphaned.
Specifically, a page is NOT considered reachable merely by existing on disk;
it MUST be linked from the sidebar tree or from another page that is itself
reachable.

#### Scenario: Formerly orphaned performance page is reachable
- **WHEN** the relocated performance content (formerly
  `docs/performance/s3-wal-backend.md`) is rendered
- **THEN** it appears under the Operations section in the sidebar

#### Scenario: Build fails if a page is unreachable
- **WHEN** a Markdown file exists under `docs/docs/` but no sidebar entry or
  in-page link references it
- **THEN** a repository link/lint check reports it as an orphan

### Requirement: Each top-level section has a landing page
Each canonical section SHALL have a Docusaurus `generated-index` landing page
(declared via its `_category_.json` `link.type`) with a one-sentence
description, so readers entering a section see an overview rather than an
arbitrary first child.

#### Scenario: Section landing pages exist
- **WHEN** each canonical section's `_category_.json` is inspected
- **THEN** it contains a `link` block with `type: "generated-index"` and a
  non-empty `description`

### Requirement: New evaluation-stage sections carry seed content
The five evaluation-stage sections SHALL each contain at least one substantive
(non-stub) page at the close of this change. The sections are Processing
Guides, Cookbook, Observability, Troubleshooting, and Migration; no canonical
section is left empty.

#### Scenario: No empty new section
- **WHEN** each of the five new evaluation-stage sections is listed
- **THEN** it contains at least one Markdown file with body content beyond a
  title and TODO placeholder
