## Context

The docs site is a Docusaurus project at `docs/` with content under
`docs/docs/`, versioned snapshots under `docs/versioned_docs/`, and an
autogenerated sidebar driven by `docs/sidebars.ts` (`{type: 'autogenerated',
dirName: '.'}`) plus per-directory `_category_.json` ordering. Three doc
versions exist (`0.5.x`, `0.3.x`, `0.2.x`). `docs/docusaurus.config.ts` sets
`onBrokenLinks: 'throw'`, so any dangling link fails the build.

The current IA (introduction → getting-started → concepts → components → sql
→ configuration → deploy → control-plane → about) is configuration-how-to
heavy and lacks the evaluation-stage sections (Cookbook, Migration,
Observability, Troubleshooting) and the concept-teaching depth (Time/Window/
State) that competing products ship. Component pages use a thin template.
`docs/performance/s3-wal-backend.md` is orphaned because `performance/` is a
sibling of the content root, not inside it.

This change is docs-only. No Rust code, config schema, or engine behavior
changes.

## Goals / Non-Goals

**Goals:**
- Establish a 12-section top-level IA that matches the structure readers
  expect from market leaders.
- Define and enforce a Vector-grade component-doc template so every component
  page is uniformly deep.
- Make component config tables drift-proof by deriving them from
  `arkflow components show --format json` / `arkflow schema`.
- Eliminate orphan pages.
- Keep the change safe to land incrementally: skeleton + template + first
  batch first, remaining content via later apply passes.

**Non-Goals:**
- Rewriting versioned docs (`versioned_docs/`) — only the current (next)
  content root is reorganized; old versions keep their frozen IA.
- Translating content to Chinese (separate change).
- Changing `sidebars.ts` away from `autogenerated` — we keep auto-generation
  and drive order through `_category_.json` + frontmatter `sidebar_position`.
- Producing every final page in this change.

## Decisions

### Decision 1: Keep `autogenerated` sidebar; drive order via `_category_.json`
**Choice**: Continue using `autogenerated` in `sidebars.ts` and express the
12-section order through numeric `position` values in each top-level
`_category_.json` (Introduction=1, Getting Started=2, … Migration=12).

**Alternatives considered**: Hand-writing `sidebars.ts` with explicit category
trees. Rejected — it duplicates ordering that `_category_.json` already
expresses and becomes stale whenever files move.

**Rationale**: Smallest surgical change; Docusaurus auto-sort already works;
the orphan problem is solved by relocating `performance/` *into* the content
root, not by abandoning auto-generation.

### Decision 2: Relocate `performance/` under the content root
**Choice**: Move `docs/performance/**` into `docs/docs/operations/` (under a
new Operations section). This makes the page reachable via auto-generation and
collapses two parallel trees into one.

**Alternatives**: Adding an explicit sidebar entry while leaving the file in
place. Rejected — it preserves a confusing two-root layout and invites future
orphans.

### Decision 3: Semi-automated component config tables with edit fences
**Choice**: Each component page's "Full reference" table is regenerated from
`arkflow components show <kind> <name> --format json` by a small generator
script. Generated blocks are wrapped in HTML comment fences
(`<!-- BEGIN AUTO: kafka-input-fields --> … <!-- END AUTO -->`) that humans
must not edit. Everything outside the fences (When to use, multi-scenario
Examples, Output schema, Error handling, Metrics, See also) is human-written.

**Alternatives considered**:
- Fully hand-written tables (current state) — rejected, this is the drift
  source.
- Docusaurus JSON-schema plugin rendering tables at build time — rejected,
  adds a heavy plugin dependency and complicates versioned builds.

**Rationale**: The CLI already emits authoritative field metadata
(`register_*_metadata` surfaced via `arkflow components show`), so deriving
tables from it is cheap; fenced blocks keep human prose and generated data in
one file without a plugin.

### Decision 4: Component template is normative, encoded in spec
**Choice**: The mandatory subsections of a component page are encoded as
requirements in `specs/docs-component-template/spec.md`, not just in this
design, so a missing section is a spec violation (enforceable at review and
via a lint script).

### Decision 5: Phased rollout gated by `docusaurus build`
**Choice**: Each phase ends with `cd docs && pnpm build` (which throws on
broken links). No phase is allowed to leave the build red.

## Risks / Trade-offs

- **[Broken internal links from moves]** → Mitigation: each phase rebuilds;
  `onBrokenLinks: 'throw'` is the gate. Use relative links (`../`) and verify.
- **[External sites link to old URLs]** → Mitigation: add `@docusaurus/plugin-client-redirects`
  entries for any moved page with a stable public URL. (See Open Questions for
  scope.)
- **[Versioned docs diverge from new IA]** → Trade-off accepted: versioned
  snapshots are frozen by design; readers on old versions see old IA.
- **[Generator script language]** → Open: pick a low-friction option for the
  repo (see Open Questions).
- **[Template burden slows page production]** → Mitigation: the "Full
  reference" table and "Status" are auto/cheap; only the prose sections need
  authoring. Template is enforced incrementally, not retroactively in one go.

## Migration Plan

No runtime migration (docs-only). Editorial migration is phased (see
`tasks.md`):

1. Phase 1 — skeleton: create new section directories with `_category_.json`
   ordering and `generated-index` landing pages; leave existing files in
   place so the build stays green.
2. Phase 2 — component template applied per component family.
3. Phase 3 — concept expansions.
4. Phase 4 — new-section first batch.
5. Phase 5 — `performance/` relocation (a single move + link fixups).
6. Phase 6 — verification (build, link check, schema-consistency check).

**Rollback**: Each phase is a set of commits under `docs/`; reverting the
phase's commits restores the prior state. No data or config migration to
undo.

## Open Questions

- **Redirects**: Should we add `@docusaurus/plugin-client-redirects` for the
  handful of pages whose public URLs change (notably the moved
  `performance/s3-wal-backend.md`), or are current URLs new enough to skip?
  Recommend: add redirects only for pages that already ship in a released doc
  version.
- **Generator language**: Node script (matches Docusaurus toolchain, repo
  already has `docs/package.json`) vs. a small Rust example binary vs. shell.
  Recommend: Node, invoked via an npm script in `docs/package.json`.
- **Status taxonomy granularity**: Stable / Beta / Experimental, or a finer
  gradation? Recommend the three-tier Vector-style set.
