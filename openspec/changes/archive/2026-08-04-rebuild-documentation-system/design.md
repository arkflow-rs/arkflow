## Context

The repository already uses Docusaurus and has useful content across getting started, concepts, components, SQL, control plane, deployment, and versioned docs. However, navigation is currently filesystem-autogenerated, the docs package exposes only generic Docusaurus commands, and link failures are not uniformly fatal. The audience includes first-time users, pipeline authors, operators, integrators, and contributors; each needs a short path to a different outcome.

The design must preserve existing Markdown/MDX content where possible, keep Docusaurus as the site engine, and make documentation quality observable in pull requests and releases. The source of truth should remain close to the implementation for component/configuration reference data, while prose stays human-authored.

## Goals / Non-Goals

**Goals:**

- Make the first successful local pipeline, production deployment, component selection, and contribution workflows discoverable from stable entry points.
- Replace implicit filesystem navigation with a curated, reviewable information architecture.
- Define a small content contract that makes pages consistent without forcing every page into a rigid template.
- Add deterministic local and CI checks for structure, links, examples, reference coverage, and version hygiene.
- Support incremental migration with redirects or compatibility stubs where page paths change.

**Non-Goals:**

- Replacing Docusaurus, introducing a separate CMS, or changing runtime configuration/API behavior.
- Rewriting all historical/versioned prose in one pass.
- Solving translations before the English information architecture is stable.

## Decisions

### 1. Use an explicit task-oriented sidebar

Create curated sidebar groups for Start Here, Build Pipelines, Understand ArkFlow, Components, Configure, Operate, Reference, and Contribute. Keep category ordering and doc IDs in `docs/sidebars.ts`; use filesystem ordering only inside deliberately generated reference groups.

Alternative considered: keep autogenerated navigation and improve filenames. Rejected because filenames cannot express persona/task priority and make accidental navigation changes invisible in review.

### 2. Separate content layers by user intent

Use stable landing pages and route pages by intent: tutorials for outcomes, how-to guides for focused tasks, concepts for system behavior, reference for exhaustive facts, and operations for deployment/troubleshooting. Existing pages will be moved or wrapped with redirects/stubs during migration rather than duplicated indefinitely.

Alternative considered: organize only by implementation module. Rejected because users start from a task such as “send Kafka data to InfluxDB,” not from the Rust crate that implements it.

### 3. Keep canonical data machine-readable and prose human-authored

Add a documented metadata/registry format for component capabilities, configuration keys, examples, and support status. A generator or checker may render tables into reference pages, but generated sections will be clearly delimited and reproducible; explanatory guidance remains authored Markdown/MDX.

Alternative considered: generate all pages from Rust source. Rejected because source signatures do not capture operational caveats, conceptual explanations, or safe examples.

### 4. Build one repository-local documentation validation command

Expose a stable `docs:check` command that runs structural checks, internal links/anchors, front matter, sidebar reachability, reference coverage, and example/config validation. CI invokes the same command, while the full site build remains a separate required job so failures are diagnosable.

Alternative considered: rely only on Docusaurus build. Rejected because build success does not prove that every supported component is documented or that examples are executable/valid.

### 5. Treat versioned docs as release artifacts

Document a current-version policy, version support matrix, archival rules, and a release checklist. New feature docs land in current docs first; version snapshots are created only at release boundaries, and pages with incompatible behavior carry explicit version/compatibility notices.

Alternative considered: continuously hand-edit all historical versions. Rejected because it creates drift and makes release review ambiguous.

## Risks / Trade-offs

- [Migration churn] Renaming pages can break external links → preserve redirects or short compatibility pages and publish a path migration map.
- [Generated reference drift] Implementation and registry can diverge → validate referenced component names against the registered implementation and fail CI on unknown or undocumented entries.
- [Checker false positives] Strict link/example checks may block useful drafts → support explicit, reviewed exemptions with an expiry/owner rather than silently ignoring failures.
- [Version maintenance cost] More explicit release rules add work → automate the checklist and keep version snapshots limited to supported releases.
- [Scope expansion] “Top-tier” quality can become an endless rewrite → define completion by measurable navigation, coverage, and CI gates; defer prose polish to follow-up changes.

## Migration Plan

1. Add the content contract, registry/checker interfaces, and curated sidebar while keeping existing doc IDs available.
2. Create landing pages and move high-traffic entry points first; add redirects or compatibility stubs for renamed paths.
3. Normalize component/configuration references and generate/check coverage.
4. Enable local checks, then make the same checks required in CI after fixing existing violations.
5. Update root README links and release guidance; validate current and versioned builds.

Rollback is by reverting the sidebar/content migration commit; generated artifacts and checker configuration must remain versioned so the revert is atomic.

## Open Questions

- Should component metadata be maintained in YAML/JSON under `docs/` or extracted from a Rust registry plus small documentation overlays?
- Which example environments (local services, Docker Compose, or mocks) are available in CI for executable integration examples?
